# CTCS-2 双站 TCC 安全联锁触发条件分析

> 文档用途：说明当前代码中哪些操作会导致安全联锁、哪些操作只会被拒绝或使列车停车，避免把“正常事务锁闭”和“故障安全锁闭”混为一谈。
>
> 分析基线：`codex/dual-station-dashboard` 分支，提交 `0a892c3`。
>
> 代码范围：`app/services/tcc_controller.py`、`app/domain/direction_change.py`、`app/services/direction_change_service.py`、`app/services/dual_train_coordinator.py`、`app/application.py`、`app/ui/dual_snapshot.py`。

## 1. 先给结论

当前程序中，“安全联锁”主要由以下八类事件产生：

1. **启动阶段尚未完成健康握手和双站全量同步**：控制器按 fail-safe 原则先锁闭。
2. **站间通信进入非 HEALTHY 状态**：包括断开、降级、连接中、握手中，以及网络错误或协议校验失败后的降级。
3. **对站状态快照由新鲜变为过期**：定时复核检测到超时后锁闭。
4. **状态同步或改方报文传输失败**：本地状态已经变化但对站无法确认时，进入故障锁闭。
5. **改方协议发现无法证明两站仍然一致**：例如方向不一致、状态版本不一致、改方事务超时、改方期间断链等。
6. **重连/全量同步安全复核失败**：通信恢复并不等于自动解锁，复核条件不满足时继续锁闭。
7. **列车运行到目的站接近区段前，目的站未建立接车进路**：A→B 时检查 `B_ARRIVE`，B→A 时检查 `A_ARRIVE`；缺失时 A、B 两站同时进入安全联锁。
8. **代码提供的显式安全事件入口被调用**：`TccController.enter_safety_lock(reason)` 会把调用方给出的原因记录为故障锁闭原因。

反过来，以下操作**不会主动制造新的安全联锁**：

- 单独建立或取消 A 站出发进路、B 站到达进路，以及两者同时建立；
- 添加待发列车；
- 因未建立发车进路、前方区段占用等普通条件不满足而拒绝发车；
- 列车运行过程中遇到普通前方区段非空闲、占用写入失败或当前区段出清失败；
- 普通的路线冲突、区段占用、分路不良导致的改方申请拒绝；
- 点击“安全复核并解除锁闭”按钮本身。该按钮只能在复核条件满足时解除锁闭，失败时保持锁闭。

## 2. 三种容易混淆的“锁闭”

### 2.1 改方事务的正常作业锁闭

字段：`direction_operation_locked=True`，但状态机阶段通常是 `WAIT_PEER`、`APPROVED` 或 `COMMITTING`。

触发方式：

- 当前方向的请求方提交改方申请；
- 对站收到合法 `PREPARE` 并预留事务；
- 对站批准后进入 `COMMITTING`；
- 双方尚未完成最终 `ACK`/应用层确认。

这是改方两阶段提交期间的**正常保护措施**，用于禁止同时办理进路、修改关键区段状态等高风险操作；它不是故障联锁，也不应被解释为“发生了事故”。事务正常完成后由 `UNLOCK` 动作释放。

### 2.2 故障安全锁闭

状态机阶段：`FAULT_LOCKED`；运行态字段：`direction_operation_locked=True`。

典型特征：

- 改方状态机进入 `FAULT_LOCKED`；
- 控制器保存 `_safety_lock_reason`；
- 通常会记录严重告警（如 `SAFETY_INTERLOCK`、`PEER_SNAPSHOT_STALE`、`DIRECTION_TRANSPORT_FAILURE`）；
- 不能靠普通按钮直接清除，必须在条件恢复后执行安全复核。

### 2.3 双站总览的聚合操作锁

`DualStationSnapshotAggregator` 会按以下条件计算 `operation_locked`：

```text
任一站通信非 HEALTHY
或两站方向不一致
或 A/B 任一站本地 direction_operation_locked=True
或共享 Q 区段双站状态不一致
```

这是总览层的只读安全门禁，不会自行修改两个 TCC 的运行态。共享区段状态不一致时，界面会禁止高风险操作、列车协调器会安全停车；只有在改方恢复/方向复核等路径实际评估到该不安全条件时，才会进一步进入本地 `FAULT_LOCKED`。

## 3. 会直接导致安全联锁的全部代码路径

### 3.1 控制器启动：先锁后同步

`TccController.__init__()` 创建改方协调器后立即调用：

```python
self._direction.on_connection_state(ConnectionState.DISCONNECTED)
```

因此，程序刚启动、尚未完成健康握手和对站全量 `STATE_SYNC` 之前，本站处于 fail-safe 锁闭。这个状态是预期的启动保护，不表示已经发生了列车运行事故。成功收到健康连接和有效双站状态后，还需要经过方向/状态一致性复核；通信恢复本身不会无条件清除锁闭。

### 3.2 站间通信进入非 HEALTHY

入口：`TccController.set_connection_state(state)`。

只要 `state != ConnectionState.HEALTHY`，控制器都会：

1. 调用 `DirectionChangeCoordinator.on_connection_state(state)`；
2. 由 `DirectionChangeMachine.disconnect()` 进入 `FAULT_LOCKED`；
3. 保存原因 `站间通信状态为 {state}，相关行车作业安全锁闭`；
4. 产生/更新 `NETWORK_UNHEALTHY` 告警；
5. 重新计算编码、信号、LEU 和 UI 快照。

因此以下网络操作都可能导致安全联锁：

| 操作/事件 | 代码入口 | 联锁效果 |
|---|---|---|
| 点击“模拟网络中断” | `ApplicationController.set_network_fault(True)` → 网络 worker 状态回调 | 两站对应控制器进入断开/降级锁闭 |
| socket 断开、连接超时、心跳异常 | `application._on_network_state` | 非 HEALTHY 状态触发本地锁闭 |
| 网络错误 | `application._on_network_error` | 先记 `NETWORK_ERROR`，再设置 `DEGRADED` 并锁闭 |
| 协议报文格式非法 | `application._report_protocol_error` | 记 `PROTOCOL_REJECTED`，设置 `DEGRADED` 并锁闭 |
| 对站全量同步校验失败 | `peer_sync.validate_and_apply` 异常分支 | 记 `PEER_SYNC_REJECTED`，设置 `DEGRADED` 并锁闭 |

`CONNECTING`、`HANDSHAKING` 也属于非 `HEALTHY`，所以处于连接建立过程时同样按安全侧锁闭；只有健康握手完成后才可能进入恢复复核。

### 3.3 对站快照从新鲜变为过期

入口：`TccController.reevaluate_time_dependent_safety()`，由应用层方向定时器周期调用。

当已有对站快照从“新鲜”跨越到“过期”时，代码执行：

```text
DirectionChangeMachine 进入 DEGRADED/FAULT_LOCKED
保存：对站状态快照已过期，相关行车作业安全锁闭
产生 CRITICAL：PEER_SNAPSHOT_STALE
```

之后即使网络稍后恢复、快照重新到达，也只会清除过期告警；方向锁闭仍需通过双方快照、方向、版本、区段和进路条件复核后解除。

### 3.4 状态同步发送失败

入口：`TccController._recalculate_and_publish()` 的 `_publish_state()` 异常分支。

当本地状态已经提交，但发送 `STATE_SYNC` 时出现 `OSError`、`ProtocolError` 或 `RuntimeError`：

- 将通信状态置为 `DEGRADED`；
- 让改方协调器执行断链锁闭；
- 产生 `NETWORK_SEND_FAILURE` 严重告警；
- 保存“状态同步发送失败：……”作为原因；
- 保留本地状态和审计记录，等待重连/全量同步恢复。

这类失败可能由任何会发布状态的操作间接触发，例如建立进路、取消进路、设置区段、信号/LEU/临时限速状态变化；**不是这些业务操作本身会锁闭，而是它们后续的状态同步发送失败会锁闭**。

### 3.5 改方报文或方向确认传输失败

入口：`TccController._direction_transport_failure()`。以下操作的发送/持久化异常都会进入该入口：

- `request_direction_change()` 发送 `PREPARE` 失败；
- `handle_direction_message()` 发送 `APPROVE`、`COMMIT`、`ACK` 或 `REJECT` 失败；
- 收到 `ACK` 后保存权威方向恢复证据失败；
- `restore_authoritative_direction()` 重发方向恢复证据失败；
- 改方 `APPLY` 前权威方向持久化失败；
- 改方响应动作发送前/发送中抛出网络或协议异常。

处理结果：设置 `DEGRADED`、进入 `FAULT_LOCKED`、产生 `DIRECTION_TRANSPORT_FAILURE` 严重告警，并保留“具体业务操作：异常信息”作为复核原因。

### 3.6 改方事务的故障条件

改方状态机使用 `_FAULT_LOCK_CODES`：

```text
COMMUNICATION_UNHEALTHY
PEER_SNAPSHOT_STALE
VERSION_MISMATCH
DIRECTION_MISMATCH
TIMEOUT
DISCONNECTED
```

在下列操作中命中这些条件，会直接进入 `FAULT_LOCKED`：

#### 3.6.1 发起改方申请时

`DirectionChangeMachine.start_request()` 的守卫失败：

- 站间通信不是 `HEALTHY`；
- 对站快照已过期。

这两类申请会被拒绝并同时故障锁闭。注意：区段占用/故障占用/分路不良（`SECTION_UNSAFE`）和活动进路冲突（`ROUTE_CONFLICT`）在**发起申请阶段只拒绝，不新建故障锁闭**。

#### 3.6.2 处理对站 `PREPARE` 时

以下情况会故障锁闭：

- 报文原方向或目标方向与本站方向矛盾：`DIRECTION_MISMATCH`；
- 报文中的申请方/响应方状态版本与本地守卫不一致：`VERSION_MISMATCH`；
- 通信非健康：`COMMUNICATION_UNHEALTHY`；
- 对站快照过期：`PEER_SNAPSHOT_STALE`。

以下情况只回绝报文，不直接锁闭：当前站不是允许的请求方、仍有恢复任务、事务 UUID/消息顺序不正确、区段不安全、存在活动进路。

#### 3.6.3 处理 `APPROVE` 或 `COMMIT` 时

以下情况会通过 `_abort_with_message()` 进入故障锁闭：

- 报文版本/事务证据不一致：`VERSION_MISMATCH`；
- 通信不健康或快照过期；
- 改方复核时区段/进路守卫不满足，但此时本站已经应用了目标方向；
- 任意错误发生在目标方向已经被应用之后。

最后一条是重要的 fail-safe 规则：目标方向一旦已经写入，不能为了“恢复正常”再回滚成旧方向；后续任何拒绝都保留当前证据并锁闭，等待恢复同步。

#### 3.6.4 处理 `ACK` 时

`ACK` 的事务、原方向、目标方向、状态版本或响应方版本任一不匹配，会按 `VERSION_MISMATCH` 故障锁闭；只有合法 `ACK` 才允许申请方最终 `APPLY` 并解除事务锁。

#### 3.6.5 改方事务超时

定时器调用 `expire_direction_change()`：

- 有活动事务且超过 `deadline_ms` → `TIMEOUT` → `FAULT_LOCKED`；
- 没有活动事务或尚未超时 → 不产生新的锁闭。

#### 3.6.6 改方期间通信中断

`DirectionChangeMachine.disconnect()` 在改方事务期间断链时按 `DISCONNECTED` 终止事务并故障锁闭；即使当前没有活动事务，收到非健康连接状态也会维持/建立故障锁闭。

### 3.7 重连、全量同步和方向复核失败

重连并不等于解锁。以下复核入口失败时会继续或重新进入故障锁闭：

| 入口 | 会锁闭的条件 |
|---|---|
| `reconcile_peer_direction(peer_direction)` | 通信不健康、快照过期、区段不安全、存在活动进路、两站方向不一致 |
| `restore_from_authority(authoritative_direction)` | 通信/快照/区段/进路守卫失败；A 站发现持久化权威方向与自身方向不一致 |
| `confirm_peer_applied(record, guard)` | 恢复校验时通信、快照、区段或进路守卫失败 |
| `recover_safety_lock()` | 仍有活动改方事务、没有双方确认方向、当前复核仍失败 |

其中，“事务记录 UUID/版本不匹配”在 `confirm_peer_applied()` 的部分路径只返回拒绝，不直接改变锁闭状态；但如果此时已落入上述不安全守卫或目标方向已经应用，仍按故障安全规则锁闭。

### 3.8 列车进入目的站接近区段但没有接车进路

入口：`DualTrainCoordinator._advance()`。

运行方向与检查规则：

| 运行方向 | 进入前需要检查的区段 | 必须存在的接车进路 | 缺失时动作 |
|---|---|---|---|
| `A_TO_B` | `B_T2`（B 站接近区段） | `B_ARRIVE` | A、B 两站同时 `enter_safety_lock(reason)`，列车停车 |
| `B_TO_A` | `A_T2`（A 站接近区段） | `A_ARRIVE` | A、B 两站同时 `enter_safety_lock(reason)`，列车停车 |

具体原因格式为：

```text
{目的站}站接车进路 {A_ARRIVE/B_ARRIVE} 未建立，列车将进入 {A_T2/B_T2} 接近区段
```

这是当前唯一由列车运行协调器主动调用双站 `enter_safety_lock()` 的业务场景。它不是“建立出发进路和到达进路时锁闭”，而是列车已经运行到目的站入口，系统发现目的站没有接车进路，继续运行会破坏进路安全条件，因此才联锁停车。

### 3.9 显式安全事件入口

任何调用：

```python
controller.enter_safety_lock(reason)
```

都会：

- 把状态机置为 `FAULT_LOCKED`；
- 设置 `direction_operation_locked=True`；
- 保存调用方提供的具体原因；
- 产生 `SAFETY_INTERLOCK` 严重告警；
- 重新计算编码、信号、LEU 和双站快照。

当前代码中，该入口由 `DualTrainCoordinator` 在缺少目的站接车进路时调用；它也应被视为后续扩展安全检测的统一锁闭入口。

## 4. 不会主动造成安全联锁的操作

### 4.1 进路操作

`RouteControlService.establish()` 对以下情况只返回失败，不调用安全锁闭：

- 方向处于锁闭状态；
- 进路方向与当前运行方向不符；
- 进路所需区段非空闲；
- 进路与已有活动进路冲突。

因此当前方向为 A→B 时，下面三种操作本身都不会制造安全联锁：

1. 只建立 A 站 `A_DEPART`；
2. 只建立 B 站 `B_ARRIVE`；
3. 同时建立 A 站 `A_DEPART` 和 B 站 `B_ARRIVE`。

B→A 时对称成立。进路建立只是列车能否发车/进入目的站的前置条件，缺少条件时在相应动作处拒绝或停车；只有列车实际进入目的站接近区段前仍缺少接车进路，才触发第 3.8 节的双站安全联锁。

### 4.2 列车演示操作

| 操作 | 当前代码行为 | 是否主动安全联锁 |
|---|---|---|
| 添加待发列车 | 创建 `WAITING` 列车，记录当前方向 | 否 |
| 发送/派发列车但未建立出发进路 | 返回“发车进路尚未建立” | 否，仅拒绝 |
| 发送/派发列车但入口区段非空闲 | 返回入口区段非空闲 | 否，仅拒绝 |
| 运行中发现普通前方区段非空闲 | 列车停车 | 否，仅停车 |
| 下一段占用写入失败 | 列车停车 | 否，除非底层状态同步发送同时失败 |
| 当前段出清失败 | 列车停车 | 否，除非底层状态同步发送同时失败 |
| 站间通信异常/方向锁闭/共享区段不一致 | `_unsafe_reason()` 使列车停车 | 该函数本身不新建锁；锁通常由通信、方向或复核路径先行产生 |
| 进入目的站接近区段而没有接车进路 | A/B 两站调用 `enter_safety_lock()` | 是，双站联锁 |

### 4.3 共享区段状态调整

共享 Q 区段的占用/空闲等状态由双方申请确认流程控制。申请生成、对站拒绝、普通条件不满足时，不会仅因为“提交申请”就造成安全联锁。若状态同步网络失败、双方状态版本不一致，或恢复/复核发现共享状态不安全，则按第 3 节的通信/版本/复核规则锁闭。

## 5. 安全复核和解除条件

顶部“安全复核并解除锁闭”按钮调用 A、B 两站的 `recover_safety_lock()`，它不是强制清零按钮。每个车站至少要满足：

1. 没有活动改方事务；
2. 已经收到双方确认的对站方向（`_peer_direction` 不为空）；
3. 当前连接为 `HEALTHY`；
4. 对站快照仍然新鲜；
5. 参与方向安全复核的区段均为 `CLEAR`；
6. 没有活动进路冲突；
7. 两站方向、状态版本和恢复证据能够一致匹配。

任一站复核失败，本站保持锁闭；双站总览仍显示安全锁闭。成功后才会清空该站 `_safety_lock_reason`、清除 `SAFETY_INTERLOCK` 告警，并由状态机产生 `UNLOCK`。

复核弹窗中的原因应优先按以下顺序展示：

```text
原始锁闭原因
→ 当前通信/快照条件
→ 当前方向与版本一致性
→ 区段或进路阻断项
→ 下一步需要完成的动作
```

例如：

```text
安全复核失败：锁闭原因：B站接车进路 B_ARRIVE 未建立，列车将进入 B_T2 接近区段；
当前复核：存在活动进路 B_DEPART，不能解除安全锁闭。
```

## 6. 用于排查的操作—结果速查表

| 操作 | 结果 | 是否进入故障安全锁闭 |
|---|---|---|
| 启动程序但尚未完成握手/全量同步 | 初始 fail-safe 锁闭 | 是（预期启动保护） |
| 模拟网络中断 | 连接降级/断开，方向锁闭 | 是 |
| 收到非法协议或全量同步校验失败 | 连接降级，严重告警 | 是 |
| 对站快照超时 | `PEER_SNAPSHOT_STALE`，列车和高风险操作受保护 | 是 |
| 发起改方，通信或快照不安全 | 申请失败并锁闭 | 是 |
| 发起改方，区段占用/活动进路 | 申请失败 | 否（本次申请不新锁） |
| 改方报文版本/方向不一致 | 故障锁闭 | 是 |
| 改方事务超时 | 故障锁闭 | 是 |
| 改方期间断链 | 故障锁闭 | 是 |
| 改方目标方向已应用后发生拒绝 | 保留证据并锁闭，不回滚 | 是 |
| 建立/取消普通进路 | 成功或拒绝 | 否 |
| 添加待发列车 | 新建待发列车 | 否 |
| 未建立发车进路就派发 | 拒绝派发 | 否 |
| 列车运行遇到普通前方占用 | 列车停车 | 否 |
| 列车进入 B_T2/A_T2 前缺少 B_ARRIVE/A_ARRIVE | A/B 同时锁闭并停车 | 是 |
| 点击安全复核按钮但条件仍不满足 | 弹出失败原因，保持锁闭 | 不改变（仍为是） |
| 点击安全复核且所有条件满足 | 清除锁闭和对应告警 | 否，恢复正常 |

## 7. 排查时应查看的代码与字段

优先查看以下字段和日志，而不要只看界面上的“安全锁闭”四个字：

- `TccSnapshot.direction_operation_locked`：本站是否被锁；
- `TccSnapshot.safety_lock_reason`：最近一次可审计锁闭原因；
- `DirectionTransactionSnapshot.phase`：是正常事务阶段还是 `FAULT_LOCKED`；
- `TccSnapshot.connection_state`：通信是否为 `HEALTHY`；
- `TccSnapshot.peer_snapshot_age_ms` / 快照新鲜度：是否已过期；
- `TccSnapshot.running_direction` 与对站方向：是否一致；
- `TccSnapshot.state_version`：两站状态版本是否存在异常差异；
- `active_route_ids`：是否存在影响复核的活动进路；
- 共享 `Q*` 区段 A/B 状态：是否一致且为 `CLEAR`；
- 告警码：`SAFETY_INTERLOCK`、`PEER_SNAPSHOT_STALE`、`NETWORK_UNHEALTHY`、`NETWORK_SEND_FAILURE`、`DIRECTION_TRANSPORT_FAILURE`、`PEER_DIRECTION_MISMATCH`。

## 8. 结论

当前实现的安全原则是“无法证明安全就不允许继续高风险行车作业”：

- **进路建立本身不是联锁触发器**；
- **列车只有在实际运行到目的站接近区段前仍没有接车进路，才由运行期检查触发双站联锁**；
- **通信、快照、方向、版本、事务和恢复证据任何一项无法确认，都可能进入故障锁闭**；
- **普通业务条件不满足时通常只拒绝或停车，不应把每一次失败都当成安全联锁**；
- **解锁必须经过条件恢复和双方安全复核，不能由 UI 强行清零**。
